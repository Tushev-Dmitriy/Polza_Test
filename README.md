# Polza Companies

Тестовое задание для Polza Agency: воспроизводимая загрузка двух наборов данных в
PostgreSQL, обработка дублей и аномалий, аналитические SQL-запросы и серверный
каталог компаний на Next.js.

> Задача 4 намеренно не включена: по условию ответы на неё кандидат должен
> написать самостоятельно, без ИИ.

## Что реализовано

- Загрузка всех 20 JSON-страниц и `review.csv`.
- PostgreSQL 17 в Docker Compose с healthcheck и автоматическим применением схемы.
- Идемпотентный импорт: повторный запуск обновляет существующие компании, а не
  создаёт копии.
- Дедупликация по исходному `id` и SHA-256-ключу из нормализованных
  `name + city + address`.
- Проверка обязательных полей, диапазона рейтинга, целочисленного числа отзывов,
  URL и кодировки текста.
- Журнал отклонённых строк `import_rejections`: грязные данные не теряются и не
  останавливают всю загрузку.
- Индексы для фильтра по городу, категории и нечёткого поиска по названию.
- Три требуемых запроса в [`sql/queries.sql`](sql/queries.sql).
- Серверная страница `/companies`: поиск, фильтр по городу, пагинация, пустое
  состояние и адаптивная таблица.
- Модульные тесты нормализации и валидации.
- Подробный разбор входных данных в [`ANOMALIES.md`](ANOMALIES.md).

## Быстрый запуск — одна команда

Понадобится только Docker Desktop. Node.js, pnpm и локальный PostgreSQL для
проверки не нужны:

```bash
docker compose up --build -d --wait
```

Команда поднимает PostgreSQL, ждёт его готовности, применяет `schema.sql`,
идемпотентно импортирует JSON и CSV, затем запускает production-сборку Next.js.
После успешного healthcheck открыть
[http://localhost:3000/companies](http://localhost:3000/companies).

Посмотреть состояние и журнал автоматического импорта:

```bash
docker compose ps
docker compose logs web
```

Остановить проект:

```bash
docker compose down
```

## Локальная разработка без контейнера приложения

Если нужно менять код с hot reload, оставьте в Docker только PostgreSQL:

```bash
docker compose up -d postgres
pnpm install
pnpm db:migrate
pnpm db:import
pnpm dev
```

Если используется npm:

```bash
npm install
npm run db:import
npm run dev
```

Значение подключения по умолчанию уже совпадает с Docker Compose:

```text
postgresql://polza:polza@localhost:5432/polza
```

Для другого PostgreSQL скопируйте `.env.example` в `.env.local` и измените
`DATABASE_URL`. Секретов в репозитории нет.

## Команды

| Команда | Назначение |
|---|---|
| `pnpm db:migrate` | Идемпотентно применить схему PostgreSQL |
| `pnpm db:import` | Последовательно загрузить JSON и CSV |
| `pnpm db:import:json` | Загрузить только `page_*.json` |
| `pnpm db:import:review` | Загрузить только `review.csv` |
| `pnpm db:report` | Показать итоги импортов и причины отклонений |
| `pnpm test` | Запустить модульные тесты |
| `pnpm typecheck` | Проверить TypeScript |
| `pnpm lint` | Запустить ESLint |
| `pnpm build` | Собрать production-версию |

Требуемые SQL-запросы:

```bash
docker compose exec -T postgres psql -U polza -d polza -f /dev/stdin < sql/queries.sql
```

В PowerShell:

```powershell
Get-Content -Raw sql/queries.sql |
  docker compose exec -T postgres psql -U polza -d polza
```

Полный сброс локальной базы:

```bash
docker compose down -v
docker compose up --build -d --wait
```

## Результат контрольного импорта

На чистой базе:

| Источник | Прочитано | Добавлено | Обновлено | Дубли | Отклонено |
|---|---:|---:|---:|---:|---:|
| 20 JSON-страниц | 1000 | 994 | 0 | 6 | 0 |
| `review.csv` | 207 | 178 | 6 | 9 | 14 |

Итого: **1172 компании**, **20 канонических городов**, **22 категории**.

Разница объясняется так:

- шесть полных дублей находятся внутри JSON;
- CSV содержит три повторные строки;
- шесть строк CSV уже присутствуют под теми же `id`;
- шесть записей `c_900...` совпадают с исходными компаниями по бизнес-ключу;
- четырнадцать строк CSV не проходят валидацию (часть строк имеет несколько ошибок).

## Схема и решения

Основная таблица `companies` хранит очищенные данные. `source_id` защищён
уникальным ограничением, а `dedupe_key` предотвращает дубли с новым ID.
Проверки PostgreSQL дублируют критические правила импортёра: рейтинг `0..5`,
неотрицательное число отзывов, непустые обязательные поля и формат ID.

Таблицы `import_runs` и `import_rejections` дают трассируемость: для каждого
запуска видны счётчики, а у каждой отклонённой строки сохраняются исходный JSON,
номер строки и точные причины. CSV с десятичной запятой `4,5` безопасно
нормализуется; очевидные варианты городов (`Moscow`, `москва`, опечатка
`Санкат-Петербург`) приводятся к каноническому виду. Неоднозначные или
повреждённые значения не исправляются догадками.

## Как проверял

Я дважды запускал импорт на одной базе и проверял, что второй запуск не увеличивает
число компаний. Затем выполнил все три SQL-запроса и сверил агрегаты с отдельным
скриптом анализа исходных файлов. На странице проверил поиск по части названия,
фильтр по Москве, их совместную работу, сброс, пагинацию и запрос без результатов.
В процессе обнаружил, что грязный CSV ломает наивное числовое преобразование, и
заменил его явной валидацией с карантином строк. Также проверил мобильную ширину,
production-сборку и поведение страницы при недоступной базе.

Скриншоты находятся в [`docs/screenshots`](docs/screenshots).

## Структура

```text

scripts/report.ts     отчёт по контрольной загрузке

sql/queries.sql       три аналитических запроса из задания

docker-compose.yml    локальный PostgreSQL
```

## Нюанс исходного ТЗ

В критериях PDF упомянуты «реальные, валидные email», однако ни JSON, ни CSV не
содержат поле email. Поэтому email не генерируются и в схему не добавляются:
выдуманные адреса ухудшили бы качество данных.
